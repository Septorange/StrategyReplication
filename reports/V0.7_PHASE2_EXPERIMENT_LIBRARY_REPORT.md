## Identity and persistence

- `run_id` is deterministic from the complete SHA-256 run identity. Repeating the same snapshot/configuration returns the same run ID.
- The default full-window evaluation ID is deterministic from the run SHA-256 and its exact window. Custom evaluations have separate IDs; both boundaries must be verified trading dates within the run's recorded history, and the end may not exceed the latest verified observation.
- SQLite stores full config hash, snapshot, status, config, artifact path, evaluation metrics/window and saved scheme metadata. Large daily/stage data remain on disk.
- Repeating both actual 12%/5bps snapshot runs returned the same complete run identity. Both runs were inserted twice with `INSERT OR IGNORE`, then reopened through a fresh library instance by resolving their on-disk `result.json`. The local library now contains two saved records: `正式 V6 12% / 商品 5bps` and `扩展快照 12% / 商品 5bps`.
- An independent common-window calculation for those saved artifacts used `2015-09-30`–`2024-11-20` (2,220 observations); both series matched exactly on that overlap. API comparison recomputes its pair metrics from the same selected rows.
- Opening a saved scheme reads SQLite metadata and its persisted `result.json`; an `artifact_manifest.json` stores the result's SHA-256 and full identity metadata, and the resolver verifies the digest, adapter version, run/config/snapshot identity and cache alias before opening. Missing or altered artifacts return explicit errors. Pairwise comparison intersects actual dates and computes both KPI sets over exactly that shared interval.
- New SQLite/cache runtime files are ignored by Git. Existing published snapshots, frozen V6, ports 8003/8004 and remote publication state were not modified.

## Mode B behavior

Mode B now accepts the active formal or published extended snapshot. P1–P4 remain disabled; only READY fields are submitted. The 12% input accepts either `12` or `0.12` and is normalized before submission. Commodity cost retains the enumerated `0/2/5/10bps` capability. The user can re-evaluate a run on an exact verified date interval, save it with a name/notes, reopen it after service restart, and compare any two saved schemes on their common interval.

The backend routes added are `POST /api/experiment/evaluations`, `POST /api/experiment/saved`, `GET /api/experiment/saved`, `GET /api/experiment/saved/{scheme_id}`, and `POST /api/experiment/compare`; the existing `POST /api/experiment` remains available and now uses the selected snapshot scope.
