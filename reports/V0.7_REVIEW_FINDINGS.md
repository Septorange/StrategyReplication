## Material findings

### [P1] The preserved Phase 3B build cannot reproduce the reported 2026-09-24 portfolio

The staged `scripts/21_build_portfolio_nav.py` calls `formal_nav_frame(p, window=load_backtest_window())`. The staged `config` directory is a symlink to the frozen V6 config, whose `config/backtest_window.yaml` has `backtest_end: "2024-11-20"` and `allow_post_end_backtest_return: false`. With the preserved code and config, rerunning this script must truncate `portfolio_daily.parquet` at 2024-11-20, not 2026-09-24.

The staged and local-snapshot artifacts do exist through 2026-09-24, and all seven reconciled Phase 3A/3B parquet files are byte-identical to the corresponding pre-existing V6 artifacts. That proves artifact coverage, but it does not prove that the saved staging recipe rebuilt the extended portfolio. The artifact therefore appears to depend on an unrecorded temporary config/code path or on copying an existing output. Preserve an explicit extended-window config and a reproducible build command, then rebuild into a fresh empty staging directory before marking Phase 1 PASS.

This is not caught by the snapshot manifest because `source_sha256` omits `src/backtest_window.py`, `config/backtest_window.yaml`, and all four staged build scripts.

An uncommitted candidate runner, `scripts/rebuild_v07_phase1.py`, appeared after this finding was reported. Its direct use of `build_portfolio_daily` addresses the formal-window truncation in principle, but it has not yet closed the finding: the saved evidence was not rebuilt from a fresh empty output directory with this runner, the runner does not enforce the existing V2 Phase 2.5 readiness/FG gates, and it does not call `validate_phase3b` even though the test report claims both checks passed. It also permits a non-empty output root, so stale optional artifacts can survive a rerun.

### [P1] `04_sync_history.py --raw-dir` is not propagated to the downloader

`04_sync_history.py` scans `args.raw_dir`, but its subprocess command invokes `02_download_history.py` without a destination argument. `02_download_history.py` always writes under its own `ROOT/data/raw`. For a non-default staging `--raw-dir`, the scan and rescan inspect staging while the actual download mutates the frozen/default raw tree.

The Phase 0 audit currently says non-dry-run writes to the caller-configured raw directory and characterizes the wrapper as a safe staging candidate. That is inconsistent with the source and is a material publication-safety risk. The audit must record this limitation; a later implementation must propagate a destination root before the wrapper can be used for staged updates.

### [P1] The frozen-hash evidence does not establish the claimed V6 immutability window

`V0.7_FROZEN_HASHES_BEFORE.json` is generated inside the report builder after the staging outputs already exist, and `AFTER` is generated later in the same reporting run. The list contains only 12 selected files. It excludes the entire raw tree, most processed outputs, `config/backtest_window.yaml`, `src/backtest_window.py`, and the staged build entrypoints.

The two files match, and the currently listed live files still match those hashes. This only proves that those 12 files did not change during report packaging. It does not support the broader report statement that no frozen V6 raw or processed file changed during the rebuild, nor can it rule out the temporary window change implicated by the first finding. Capture a full scoped baseline before the build and compare it after the build, including every symlink target and all raw/processed files in the frozen boundary.
