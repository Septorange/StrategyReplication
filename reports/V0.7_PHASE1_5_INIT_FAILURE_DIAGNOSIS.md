# V0.7 Phase 1.5 — initialization failure diagnosis

**Status: PARTIALLY VERIFIED.** The reported browser `Load failed` could not be reproduced against a live local server in this run. Starting the site on an unused diagnostic port reached Uvicorn startup but the sandbox denied the localhost bind (`operation not permitted`); the browser session available to inspection was on an unrelated page. API behavior was instead exercised through FastAPI's in-process ASGI test transport.

The code confirms a failure mechanism that can produce the observed all-page failure: `frontend/app.js` awaited core pages, research metadata, drawdowns, exposure data, and parameter metadata in one `Promise.all`. Any rejected non-core request rejected `init()` and left the page in the generic initialization error state. This mechanism is now removed. Summary, rules, series, and assets form the required first-screen group; research metadata and secondary panels load with `Promise.allSettled`. A core failure names the URL and either the HTTP status/body excerpt or network error and provides an initialization retry. A later page failure is local to that page and has its own retry.

The exact endpoint that failed during the user's earlier browser session remains **NOT VERIFIED** because no browser Network log, server traceback, or live localhost request was available. No missing data has been replaced with mock values, and failed core data does not select the system date.

The backend now tolerates missing or malformed formal snapshot inputs during module initialization. `/api/health` and `/api/data/status` report a degraded state with non-sensitive diagnostic codes, while data routes return an explicit 503. The formal baseline remains the only selectable snapshot.
